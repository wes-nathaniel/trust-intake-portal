# RCA — Claude.ai "connection error immediately" on MCP OAuth (trust.igchq.com/api/mcp)

## Summary
The MCP server itself is healthy and every endpoint returns correct status, body, and CORS. Claude's failure is a **discovery-path** problem, not a backend/WAF block. Two distinct faults were found; a redeploy (run `bab16436-...`) picked up an updated source that FIXED one of them. One fault remains.

## What was verified (evidence)
- Deployment is `cloudflare` frontend: claude.ai -> Cloudflare custom hostname (trust.igchq.com) -> Cloudflare worker -> k8s FastAPI backend. Worker routing is "/api/* -> backend, everything else -> R2 static".
- Backend logs show Claude's real requests DO reach origin (proxy hop IP 34.49.222.149) and get correct codes: `POST /api/mcp` 401, `OPTIONS /api/mcp` 200, `oauth/register` 201, `oauth/authorize` 200, both well-known docs 200. **=> Cloudflare is NOT hard-blocking Claude's UA/IP.** Hypothesis (a) disproven.
- Live probe with `Origin: https://claude.ai`:
  - `POST /api/mcp` 401 carries BOTH `access-control-allow-origin: https://claude.ai` AND `www-authenticate: Bearer resource_metadata="https://trust.igchq.com/api/mcp/.well-known/oauth-protected-resource"`, `content-type: application/json`, `vary: Origin`, JSON-RPC body `{"jsonrpc":"2.0","id":null,"error":{"code":-32001,...}}`. **=> Hypothesis (4) and (b)/(c) on the 401 body/CORS disproven.** (curl "works" only because curl sends no Origin, so it never exercises CORS.)
  - OPTIONS preflight echoes the exact headers Claude sends (`authorization, content-type, mcp-protocol-version, mcp-session-id`) with ACAO + credentials. No header-allowlist issue.
  - AS metadata is fully spec-complete: `code_challenge_methods_supported:["S256"]`, grant_types, `registration_endpoint`, `client_id_metadata_document_supported:true`.

## Fault #1 (FIXED by this redeploy)
Before redeploy, the 401 had NO `access-control-expose-headers`, so claude.ai's browser fetch could not read the `WWW-Authenticate` header and could not follow its `resource_metadata` pointer. After redeploy, the live 401 now returns:
`access-control-expose-headers: WWW-Authenticate, Mcp-Session-Id, MCP-Protocol-Version, Retry-After`.
Claude can now read the pointer to the working path-appended metadata URL. This was an app-source change shipped in run `bab16436`.

## Fault #2 (STILL OPEN — needs a code/worker fix)
The server only hosts OAuth/MCP discovery metadata at the **path-APPENDED** (OIDC-style) locations under `/api/`:
- `GET /api/mcp/.well-known/oauth-protected-resource` -> 200
- `GET /api/mcp/oauth/.well-known/oauth-authorization-server` -> 200

But RFC 9728 / RFC 8414 (and MCP clients, incl. Claude) construct metadata URLs by **INSERTING** `/.well-known/...` between host and path. Those URLs are NOT under `/api/`, so the Cloudflare frontend worker serves them from R2 and returns **403** (never reaching FastAPI). Confirmed live, post-redeploy:
- `GET /.well-known/oauth-protected-resource/api/mcp` -> **403**
- `GET /.well-known/oauth-authorization-server/api/mcp/oauth` -> **403**
- `GET /.well-known/openid-configuration/api/mcp/oauth` -> **403**
- (`GET /api/mcp/oauth/.well-known/openid-configuration` -> 404 from backend — harmless)

A 403 (vs a clean 404) can cause strict OAuth clients to treat the authorization-server as "exists but forbidden" and abort discovery before opening the login popup. With Fault #1 now fixed, Claude may succeed via the path-appended fallback — **retest first**. If Claude still errors, Fault #2 is the cause.

## Recommended fix for Fault #2 (E1 / code + Cloudflare worker)
Make the RFC-inserted well-known URLs return the same 200 JSON as the path-appended ones. Two coordinated changes:
1. Backend: add routes serving the metadata at the root-level RFC paths:
   - `/.well-known/oauth-protected-resource/api/mcp` (and `/.well-known/oauth-protected-resource`)
   - `/.well-known/oauth-authorization-server/api/mcp/oauth` (and `/.well-known/oauth-authorization-server`)
2. Cloudflare frontend worker routing (manifest: build-frontend-artifacts.sh / worker): proxy `/.well-known/oauth-protected-resource*` and `/.well-known/oauth-authorization-server*` to the k8s backend instead of serving them from R2 (which yields the 403). Without this, backend routes alone won't be reached for those paths.

## Items that are NOT the cause (ruled out)
- Cloudflare WAF/UA/IP block — disproven (requests reach origin, get 200/201/401).
- 401 JSON-RPC body / Content-Type — correct.
- Missing ACAO / www-authenticate on the same response — both present.
- Missing Mcp-Session-Id / header allowlist — preflight allows them.
- OAuth metadata completeness — complete (PKCE S256, DCR, CIMD all advertised).

Per explicit user instruction, redeployed via resume_pipeline. New run `bab16436-cb26-47e7-a08d-c6345eb639d4` succeeded and is live at https://trust.igchq.com. This shipped the Fault #1 fix (expose-headers). It did NOT fix Fault #2.
