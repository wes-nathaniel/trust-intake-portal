### 4. Blocking I/O beyond get_object — THE FIX IS INCOMPLETE
Two important facts:
- **`get_object`/`put_object` are NOT boto3/S3 clients.** They are synchronous `requests.get(..., timeout=60)` / `requests.put(..., timeout=120)` to the storage service (server.py lines 287–304). Each also calls `init_storage()`, which itself makes a blocking `requests` call. These block the event loop when not offloaded.
- **Only 1 of 12 `get_object()` call sites was wrapped** in `asyncio.to_thread` — line 5098, the viewer page-render endpoint `GET /api/trust-cases/{case_id}/trust-preview/page/{page}.png`. The claim that *all* synchronous `get_object()` calls were wrapped is incorrect.

Remaining **raw/blocking** `get_object()` calls (11): lines 3348, 4151, 4501, 4523, 4554, 4645, 4766, 5043, 5137, 5199, 6823.  
Remaining **raw/blocking** `put_object()` calls (4): lines 3271, 4295, 4708, 4814.

Directly relevant to the PDF viewer symptom (all stream a whole PDF synchronously, freezing the loop for the duration of the download):
- line 5137 `GET /api/admin/trust-cases/{case_id}/trust-draft/raw` (admin raw draft download)
- line 5199 `GET /api/trust-cases/{case_id}/trust-final` (client final trust download)
- line 3348 `GET /api/trust-cases/{case_id}/documents/{doc_id}/download`
- lines 4151/4501/4523/4554/4766 — admin extract / page-explanation / regenerate jobs that fetch the full PDF inline before starting the background job.

Other blocking I/O: **Stripe calls are synchronous** (the stripe lib issues blocking HTTP; `/api/admin/stripe/health` is polled frequently, plus product/price lookups at startup) and are not offloaded — each blocks the loop ~200–300ms. MongoDB access uses motor (`await db…`) and is correctly async — not a concern.

### 5. uvicorn worker count — PRODUCTION RUNS 1 WORKER, NOT 2
Startup log, both pods: `Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1`.

Why the "bump to 2" never took effect: `entrypoint.sh` extracts the launch command from `CONFIG_FILE=/app/etc/supervisor/conf.d/supervisord.conf`. That file (shipped into the image from `etc/…` via `COPY . /app`) is the **preview, platform-managed, "READONLY — DO NOT EDIT"** config and contains `--workers 1 --reload` (entrypoint strips `--reload`, leaving `--workers 1`). The developer's edit was made to a **different** file — `backend/supervisord.conf` (`--workers 2`) — which the entrypoint never reads. So the worker bump is dead code in production.

## Root cause
With a single uvicorn worker (one event loop) and ~15 synchronous storage calls + synchronous Stripe calls still running on that loop, any one blocking PDF download / storage round-trip / Stripe call freezes the loop. The viewer requests multiple `page/{page}.png` images concurrently; while the loop is frozen those requests stall and can hit the proxy timeout → pages intermittently fail to appear. The P0 fix hardened only the page-render path and did not address (a) the other 15 blocking storage calls, or (b) the worker count, which is still 1 because the edit landed in the wrong file.

## Required fixes
1. **Code (E1):** Wrap ALL remaining `get_object()`/`put_object()` call sites in `await asyncio.to_thread(...)` — the 11 + 4 lines listed above — prioritizing the PDF-serving/download endpoints (5137, 5199, 3348) and the inline-fetch job endpoints (4151, 4501, 4523, 4554, 4766). Consider offloading the synchronous Stripe calls too (or use an async path), as they also block the single loop.
2. **Worker count:** The production launch command comes from `/app/etc/supervisor/conf.d/supervisord.conf` (workers 1), not `backend/supervisord.conf` (workers 2). To actually run 2 workers, the launch path (`entrypoint.sh` / the shipped supervisor config) must be changed — editing `backend/supervisord.conf` has no effect. This is a deployment-launch/manifest concern; raise via the deployment manifest/entrypoint or Emergent support since the read file is platform-managed. Note: completing fix #1 is the primary remedy for the symptom; the worker bump is a secondary mitigation.
