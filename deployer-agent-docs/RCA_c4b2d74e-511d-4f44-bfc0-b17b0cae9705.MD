# RCA — trust.igchq.com intermittent trust-document / PDF failures

**Deployment:** trust-intake-portal  (active run `c4b2d74e-511d-4f44-bfc0-b17b0cae9705`, tier_2 "Grow", Cloudflare frontend)
**Symptom reported:** Trust draft viewer and PDF downloads "sometimes do not show up."
**Mode:** Read-only investigation. No data or config modified.

---

## TL;DR — Root cause (confirmed by source inspection)

The trust-document **download** endpoints call a **blocking, synchronous** object-storage read (`get_object()`, `requests.get(..., timeout=60)` + a `requests.post` storage-init `timeout=30`) **directly on the asyncio event loop**, reading the whole PDF into memory. Production runs uvicorn with **only one worker per pod** (confirmed in runtime logs), so while one such download is in flight, that pod's single event loop is blocked and **every other request on that pod stalls or 503s** — including the trust-preview viewer pages and `/health`. This is the intermittent "sometimes it doesn't show up."

A second aggravator: the per-pod in-memory PDF/image caches are wiped on every deploy/pod restart, so the first viewer load after each of the frequent recent redeploys is a cold full re-download + re-render (slow first load).

Note on the worker count: `backend/supervisord.conf` was deliberately set to `--workers 2` ("so a single long-running request doesn't block"), but the deployed `entrypoint.sh` reads its command from the platform file `/app/etc/supervisor/conf.d/supervisord.conf`, which is pinned to `--workers 1`. Runtime log confirms `uvicorn server:app ... --workers 1`. **Editing `backend/supervisord.conf` has no effect in production.**

## Evidence by investigation item

### 1. Backend runtime / error logs (last 24h)
- The active run was deployed **2026-11-10 23:42** (Cloudflare redeploy), so only ~70 min of pod logs exist in the window — older runs' pods are gone. **LIMITATION: I cannot see logs from the exact times the user hit failures on prior runs.**
- In the available window: **352× HTTP 200**, **zero 5xx on API routes**, **no tracebacks/exceptions**, no explicit timeout lines.
- Only errors present: **3× nginx `connect() failed (111: Connection refused)` to `127.0.0.1:8001/health`** at 23:42:06–23:42:21 — transient cold-boot window before uvicorn bound. Normal for a rollout.
- uvicorn access logs do not record request durations, so a >3s slow request produces no explicit log line — the stall mechanism (below) would not self-report as an error.
- The viewer/download endpoints were not exercised during this short window, so no PDF failures were captured live.

### 2. Restarts / sleep / cold starts
- 2 replicas, `restart_count: 0`, no OOMKilled, no eviction.
- tier_2: `replicas: 2`, `max_replicas: 2`, **HPA disabled → NO scale-to-zero. The app does NOT sleep.**
- Cold starts occur **only on deploy rollout**: image pull (35–47s) + uvicorn start + 4 Stripe catalog API calls during lifespan startup (~1–2s). nginx returns 503 for ~10–15s until uvicorn binds (the "connection refused" lines).
- **VPA is enabled** → VPA may occasionally evict/restart a pod to retune resources (none observed recently; restart_count=0).
- Avoiding cold starts: reduce deploy frequency, and note that each deploy/restart wipes the per-pod in-memory caches (see item 5).

### 3. CORS
- **Correctly configured — not the cause.** `CORSMiddleware` `allow_origins` includes `https://trust.igchq.com` (plus FRONTEND_URL and the preview origin), `allow_credentials=True`, methods/headers `*`.
- No CORS/OPTIONS 4xx in logs. With the Cloudflare frontend, app + `/api` are same-origin on trust.igchq.com, so preflight is largely moot.

### 4. Session / auth cookies
- `set_cookie` uses `httponly=True, secure=True, samesite="none"`, no explicit `domain` (host-scoped to trust.igchq.com). `samesite=none`+`secure` is valid for same-site and cross-site; same-origin Cloudflare serving means cookies are sent reliably. No Set-Cookie domain mismatch between trust.igchq.com and the preview origin.
- There is an **idle-session timeout** (inactivity → 401). An idle user could perceive "doesn't show up" after logout, but that's by-design, not a cookie bug. Not the primary cause.

### 5. Trust draft viewer + PDF endpoints — ROOT CAUSE
Endpoints (server.py):
- Viewer: `GET /api/trust-cases/{id}/trust-preview/page/{n}.png` — renders PDF→JPEG (PyMuPDF). **This one is correct**: it offloads `get_object` + render to `asyncio.to_thread` and caches. Errors surface as 502 "Could not read PDF from storage" / 500 "Failed to render preview".
- Downloads (THE PROBLEM): `GET /api/admin/trust-cases/{id}/trust-draft/raw` (line 5137), `GET /api/trust-cases/{id}/trust-final` (line 5199), `GET /api/trust-cases/{id}/documents/{doc_id}/download` (line 3348), and several admin/explainer paths (lines 4151/4501/4523/4554/4645/4766/5043/6823) call **synchronous blocking `get_object()` directly on the event loop** and buffer the whole file into `io.BytesIO` before streaming.
- `get_object()` (line 297): `init_storage()` → `requests.post(.../init, timeout=30)` then `requests.get(.../objects/{path}, timeout=60)`. Worst case ~90s of blocking I/O **on the event loop**.
- With one uvicorn worker per pod, a single large/slow PDF download (or a slow storage call) blocks that pod's event loop, stalling all concurrent requests on that pod — viewer pages, API calls, `/health`. Round-robin across 2 pods makes it intermittent and user-specific → **"sometimes it does not show up."**
- No max-file-size guard; whole PDF buffered in memory → memory spikes under concurrency (tier_2 limit 4Gi; not currently OOMing but a risk).

### 6. Worker / concurrency mismatch (amplifier)
- `backend/supervisord.conf`: `--workers 2` (dev intent). **Not used in production.**
- Deployed `entrypoint.sh` reads `/app/etc/supervisor/conf.d/supervisord.conf` (marked "READONLY FILE, DO NOT EDIT"), which is `--workers 1 --reload`; entrypoint strips `--reload` → **`--workers 1`**.
- Runtime log: `Starting FastAPI backend: uvicorn server:app --host 0.0.0.0 --port 8001 --workers 1`. Confirmed.

### 7. MongoDB connection pool
- `client = AsyncIOMotorClient(mongo_url)` with **default settings** (no maxPoolSize/timeouts tuned; motor default pool 100).
- **No pool-exhaustion or ServerSelectionTimeout errors** in the available logs. Not implicated by evidence (window limited).
- Minor: an idle-timeout check does an extra DB read per request and swallows DB errors ("idle-timeout check DB error (allowing request)").

### Recently deployed (context)
- 5 redeploys Nov 6–10 (asset/account-number feature in progress, Zelle change, credit-repair removal). `asset-items` endpoints are serving 200.
- Each redeploy wipes the **per-pod** in-memory PDF/page caches (`_PDF_BYTES_CACHE_MAX=5`, `_PREVIEW_CACHE_MAX=200`) → first viewer load after each deploy is a cold full re-download + re-render. Frequent deploys = frequent cold first-loads.

## Fixes

### Primary — Code (E1)
Make object-storage reads non-blocking in the download endpoints so one download can't freeze the pod:
- Wrap every request-path `get_object()` call in `await asyncio.to_thread(get_object, ...)` — mirror the existing fix in `trust_preview_page`. Call sites: server.py lines **3348, 5137, 5199** (user-facing downloads) and **4151, 4501, 4523, 4554, 4645, 4766, 5043, 6823**.
- Preferably stream the storage response instead of buffering the whole PDF into `io.BytesIO` (reduces memory spikes on large files).
- This makes the single-worker runtime safe and removes the intermittent stall.

### Code note (E1)
- `backend/supervisord.conf --workers 2` does NOT reach production; the platform runs `--workers 1`. Do not rely on editing that file to fix concurrency — the `asyncio.to_thread` change above is the correct fix.

### Operational (User)
- Reduce redeploy frequency where possible; each deploy cold-wipes the per-pod PDF/image caches (slow first load). Optionally move the per-pod cache to a shared/warm cache if cold first-loads remain painful.
- To pinpoint any residual case, capture one failing request in the browser Network tab (endpoint, status, timing) while reproducing.

### Not the cause (ruled out)
CORS, cookie/domain config, MongoDB pool, pod sleep/scale-to-zero, OOM, and the custom-domain DNS/SSL (verified, SSL active) are all healthy.

**Reproduction note:** The blocking-call behavior is confirmed by source inspection. It was NOT reproduced at runtime because the eph sandbox has no live object-storage credentials, so the storage stall cannot be exercised there.
